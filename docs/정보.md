# NaVi 정보 정리

## 1. 서비스 개요

### 1.1 서비스명
**NaVi**

### 1.2 서비스 정의
NaVi는 **안양시 공공데이터와 접근성 정보를 기반으로 실제 통과 가능한 보행경로를 계산하고, 주요 이동 지점에서 AR로 행동을 안내하는 이동약자 보행 내비게이션 서비스**다.

단순한 길찾기 앱이나 AR 앱이 아니라 다음 기능을 하나의 흐름으로 연결한다.

> 공공데이터 및 현장 정보  
> → AI 기반 상태 판단  
> → 접근성 상태 관리  
> → 보행 그래프 기반 경로 탐색  
> → 우회·재탐색 판단  
> → AR 행동 안내

### 1.3 핵심 문제
일반 지도 서비스는 대체로 **최단·최속 경로**를 계산한다.

NaVi가 다루는 핵심 질문은 다르다.

> **“지금 이 사용자가 실제로 통과할 수 있는 길은 어디인가?”**

따라서 NaVi는 단순 경로 길이뿐 아니라 다음을 함께 고려한다.

- 공사 및 통행 차단
- 턱·계단 등 이동 제약
- 횡단보도
- 접근 가능한 출입구
- 현재 확인되지 않은 구간
- 데이터의 최신성
- 사람 검수 여부

# 2. 서비스 포지셔닝

## 2.1 자동차 AR Navigation·ADAS와의 관계

NaVi의 기술 구조는 자동차의 **AR Navigation 및 ADAS(Advanced Driver Assistance System)** 와 유사한 형태를 가진다.

| 자동차 ADAS / 자율주행 | NaVi |
|---|---|
| 차량 위치 추정 | 사용자 위치 추정 |
| HD Map | 보행 접근성 그래프 |
| 차선·장애물 인식 | 공사·턱·차단·횡단보도 등 인식 |
| 도로 상태 판단 | 보행 구간 상태 판단 |
| Path Planning | 접근 가능 경로 탐색 |
| 경로 재계산 | 접근성 상태 기반 재탐색 |
| AR HUD | 스마트폰 AR Guidance |
| 조향·가속·제동 | 사용자의 실제 이동 행동 |

가장 큰 차이는 마지막 단계다.

### 자동차
```text
환경 인식
→ 판단
→ 차량 제어
```

### NaVi
```text
환경 인식
→ 판단
→ AR 안내
→ 사람의 행동
```

따라서 NaVi는 완전자율 시스템이 아니라 **Human-in-the-loop 보행 지원 시스템**으로 보는 것이 정확하다.

## 2.2 내부 기술 개념
내부적으로는 다음 표현이 적합하다.

> **Pedestrian ADAS**
>
> 보행자를 위한 이동 의사결정 지원 시스템

단, 사용자-facing 서비스명이나 공모전 제목에 ADAS를 직접 넣는 것은 자동차 기술로 오해될 수 있으므로 권장하지 않는다.

# 3. ON:WAY와 NaVi의 차이

## 3.1 ON:WAY의 성격
ON:WAY는 접근성 데이터와 이동 분석 자체가 중심이었다.

```text
접근성 데이터 수집
→ 보행·환승 위험 분석
→ 접근 가능한 경로 계산
→ 현장 실증
→ 필요 지점에서 AR 안내
```

주요 가치는 다음과 같았다.

- 보행 네트워크 구축
- 정류장·환승 위험 분석
- 저상버스 및 교통약자 이동 분석
- 우회비율 및 추가시간 계산
- route confidence
- assistance required
- 실증 기반 경로 비교

즉 ON:WAY는 성격상 **접근성 이동 데이터·분석 플랫폼**에 가까웠다.

## 3.2 NaVi의 성격
NaVi는 같은 접근성 문제를 보다 좁고 구체적인 **시민용 제품**으로 전환한 프로젝트다.

ON:WAY의 질문이

> “이동 위험은 어디에 있는가?”

였다면, NaVi의 질문은

> **“지금 어디로 이동해야 하는가?”**

에 더 가깝다.

따라서 NaVi에서는 경로 분석 결과를 실제 행동으로 전달하는 인터페이스가 중요해졌고, 이 역할을 AR이 담당한다.

# 4. ON:WAY보다 NaVi에서 AR 비중이 커진 이유

## 4.1 기술의 본질이 바뀐 것은 아님
AR의 기술적 비중이 급격히 커진 것이 아니라, **사용자 체감과 데모에서의 중요도가 커진 것**이다.

NaVi의 핵심 아키텍처는 여전히 다음과 같다.

```text
공공데이터
+
현장 관측 데이터
        ↓
AI 상태 판단
        ↓
접근성 상태 관리
        ↓
보행 그래프
        ↓
접근성 경로 탐색
        ↓
행동 결정
        ↓
AR 안내
```

AR은 이 구조의 마지막 계층이다.

따라서:

> **접근성 경로 엔진 = Brain**  
> **AR = Interface**

로 보는 것이 적절하다.

## 4.2 시민이 차이를 즉시 이해할 수 있음
지도만 보여주면 기존 지도 서비스와 NaVi의 차이가 직관적으로 드러나지 않을 수 있다.

반면 AR에서는 다음과 같이 판단 결과가 행동으로 바로 연결된다.

```text
앞 구간 공사
통행 제한

← 오른쪽으로 우회하세요

추가 거리 +72m
```

이 한 화면만으로도 NaVi가 단순 지도 앱이 아니라는 점을 보여줄 수 있다.

## 4.3 구현 범위가 좁아짐
ON:WAY는 정류장·환승·보행·저상버스·시설 등 도시 이동 전반을 다뤘다.

NaVi는 안양시 특정 지역·특정 경로를 중심으로 MVP를 구현할 수 있다.

예:

```text
안양역
→ 횡단보도
→ 공사구간
→ 목적지
```

범위가 좁아지는 대신 사용자 경험과 AR 완성도를 높일 수 있다.

## 4.4 공모전에서는 시제품 완성도가 중요
NaVi는 실제로 “시민이 어떻게 사용하는가”를 보여주는 것이 중요하다.

따라서 AR은 시스템에서 가장 큰 기술은 아니지만 **가장 잘 보이는 기술**이 된다.

### 권장 비중
| 구성 요소 | 권장 비중 |
|---|---:|
| 공공데이터·접근성 상태 구축 | 25% |
| AI 현장 판단·검수 | 20% |
| 접근성 경로 탐색 | 25% |
| AR Navigation | 20% |
| 사용자 UX·근거 표시 | 10% |

다만 발표·시연에서는 AR 화면을 더 많이 보여줄 수 있다.

- 기술 비중: 약 20%
- 사용자 체감: 약 30%
- 발표·데모 화면 비중: 약 40~50%

# 6. AR의 역할

## 6.1 AR은 장식 기능이 아님
NaVi에서 AR은 단순히 화살표를 예쁘게 보여주는 기능이 아니다.

> **Decision을 실제 사용자 행동으로 변환하는 인터페이스**

다.

예:

```text
← 이쪽으로 이동하세요

앞 구간
⚠ 공사로 통행 제한

우회 거리 +72m
```

일반 AR 내비게이션이

> “20m 후 좌회전”

이라고만 안내한다면,

NaVi는

> “20m 후 좌회전 — 앞 구간의 통행 제한을 피하기 위한 경로입니다.”

처럼 **행동 + 이유**를 함께 제시한다.

## 6.2 항상 AR을 사용하는 것은 아님
도시 전체에서 AR 카메라를 계속 켜는 방식은 비현실적이다.

AR은 판단이 필요한 핵심 지점에 집중한다.

### AR Mobility Point 예시
- 복잡한 교차로
- 횡단보도
- 공사 구간
- 우회지점
- 엘리베이터
- 건물 출입구
- 방향전환이 어려운 구간

사용 흐름:

```text
지도 기반 이동
↓
Mobility Point 접근
↓
AR 활성화
↓
행동 안내
↓
통과
↓
일반 지도 이동
```

# 7. UI/UX 방향

## 7.1 UX 핵심 원칙
NaVi는 일반 지도 앱과 다르게 다음 네 가지 원칙을 가져간다.

1. **빠른 길보다 통과 가능한 길**
2. **결과만이 아니라 판단 근거 제공**
3. **AI가 직접 확정하지 않고 검수 가능한 구조**
4. **불확실성을 숨기지 않음**

## 7.2 핵심 UX 구조
사용자 흐름은 다음 세 단계로 구성한다.

### Plan
출발 전에 경로를 설정한다.

- 목적지 검색
- 이동 조건 설정
- 추천 경로 확인

### Navigate
이동 중에는 지도와 AR로 안내한다.

- 직진
- 좌회전
- 횡단
- 우회
- 재탐색

### Explain
필요하면 판단 근거를 확인한다.

- 왜 우회했는가
- 왜 이 횡단보도를 선택했는가
- 언제 확인된 정보인가
- 사람 검수가 완료되었는가

즉:

> **Plan → Navigate → Explain**

구조를 NaVi UX의 기본 틀로 사용한다.

# 8. 시민용 핵심 화면

## 8.1 홈 화면
목적지를 빠르게 입력하고 이동 조건을 설정한다.

```text
NaVi

갈 수 있는 길을
눈앞에서 안내합니다.

[ 출발지 ]
[ 목적지 ]

이동 조건
□ 계단 피하기
□ 높은 턱 피하기
□ 공사 구간 피하기
□ 접근 가능한 출입구 우선

[ 길찾기 ]
```

장애유형을 직접 묻기보다는 **이동 조건을 묻는 방식**을 우선한다.

## 8.2 경로 결과
NaVi의 판단 결과를 가장 명확하게 보여주는 핵심 화면이다.

```text
안양역 → 목적지

접근 가능한 추천 경로
1.24 km · 약 18분

✓ 통과 확인 12
! 우회 구간 1
? 확인 필요 2

일반 경로보다 +140m

[ 지도 ]

왜 이 경로인가요?
일반 경로의 횡단보도 1곳이
통행 제한 상태로 확인되어 우회합니다.

[ AR 안내 시작 ]
```

### 핵심 비교
- 일반 경로: 1.10 km / 15분
- NaVi 경로: 1.24 km / 18분
- 차이: +140m
- 이유: 차단 구간 회피

이 비교는 공공데이터와 접근성 상태가 실제 경로에 영향을 주었다는 점을 직관적으로 보여준다.

## 8.3 AR Navigation
NaVi의 Hero Screen이다.

```text
          ↑
      24m 직진

   [ 횡단보도 ]
    통과 확인

────────────────

다음 행동
왼쪽 횡단보도를 이용하세요.

✓ 최근 확인됨
```

우회 상황:

```text
← 이쪽으로 우회하세요

앞쪽 보도
⚠ 공사로 통행 제한

우회 거리 +72m
```

## 8.4 구간 상세
특정 보행 구간의 상태와 근거를 보여준다.

```text
횡단보도 CW04

⚠ 통행 제한 가능

공사 차단물
────────────────
상태       확인됨
확인일     2026.09.15
검수       사람 확인 완료

이 구간 때문에
경로가 146m 우회됩니다.

[ 근거 보기 ]
```

미확인 구간:

```text
? 현재 상태를 확인할 수 없습니다

공개데이터에 접근성 정보가 없고
현장 자료에서도 충분히 확인되지 않았습니다.

NaVi는 확인되지 않은 구간을
안전하다고 판단하지 않습니다.
```

# 9. 관리자 UI

관리자 화면은 별도의 복잡한 SaaS 제품처럼 만들기보다 **같은 지도 + 검수용 Side Panel** 구조를 사용한다.

```text
NaVi Admin

[ 지도                         ] [ 검수 대기 12 ]
                               [ 재확인 필요 8 ]
                               [ 통행 제한 4 ]

                               검수 우선순위
                               1. CW04-A
                               공사 후보
                               영향 경로 6개

                               [ 검수 시작 ]
```

검수 화면:

```text
CW04-A

[ 현장 이미지 ]

AI 사전판독
공사 차단 후보

신뢰도 0.82

현재 판단
○ 통과
○ 통행 제한
○ 확인 불가

판단 사유
[                ]

[ 검수 완료 ]
```

핵심은 다음 위계를 명확히 보여주는 것이다.

> **AI 사전판독 → 사람 검수 → 승인된 상태만 경로 반영**

# 10. 상태 체계

내부 상태와 사용자 표현을 분리한다.

| 내부 상태 | 시민 UI |
|---|---|
| verified_pass | 통과 확인 |
| verified_block | 통행 제한 |
| candidate | 확인 중 |
| unknown | 정보 없음 |
| stale | 재확인 필요 |

표현은 색만 사용하지 않고 항상 **아이콘 + 텍스트 + 색상**을 함께 사용한다.

예:

- ✓ 통과 확인
- ! 통행 제한
- ? 정보 없음
- ↻ 재확인 필요

# 11. 컬러 시스템

## 11.1 브랜드 컬러
NaVi는 **Blue + Violet**을 중심으로 한다.

| 역할 | HEX | 용도 |
|---|---:|---|
| Primary Blue | `#2563EB` | CTA, 경로, 핵심 액션 |
| Deep Navy | `#172554` | 제목, 본문, 정보 |
| NaVi Violet | `#7C3AED` | 브랜드 포인트, AR target |
| Soft Blue | `#EFF6FF` | 카드 및 선택 상태 |
| Background | `#F8FAFC` | 전체 배경 |
| White | `#FFFFFF` | 카드 |

화면 전체에서는 다음 비율을 권장한다.

- 80%: White / Gray / Navy
- 15%: Blue
- 5%: Violet

## 11.2 상태 컬러
브랜드색과 상태색을 분리한다.

| 상태 | 색 | HEX |
|---|---|---:|
| 통과 확인 | Teal | `#00866A` |
| 통행 제한 | Red | `#DC2626` |
| 확인 필요 | Amber | `#D97706` |
| 정보 없음 | Gray | `#64748B` |

## 11.3 지도 컬러
- 추천 경로: Blue
- 일반 경로: Light Gray
- 우회 구간: Violet
- 차단 구간: Red + X / 사선

# 12. 캐릭터 방향

## 12.1 캐릭터의 역할
NaVi 캐릭터는 서비스의 주인공이 아니라 **작은 AI Co-pilot / 안내자** 역할을 한다.

캐릭터 중심의 귀여운 앱보다 **길·공간·상태 정보가 주인공**이 되어야 한다.

## 12.2 형태
권장 형태:

> **Butterfly + Map Pin + Navigation Arrow**

- 몸통: 지도 Pin
- 날개: 두 갈래 Path
- 하단: Navigation Arrow
- 얼굴: 눈 2개 정도의 매우 단순한 표현

### 지양
- 팔·다리 과다 표현
- 옷·모자·가방
- 어린이용 캐릭터 스타일
- 휠체어를 탄 캐릭터
- 장애를 직접 상징하는 외형

캐릭터는 특정 사용자를 대표하기보다 **길을 안내하는 시스템**을 상징해야 한다.

## 12.3 캐릭터 색
- 왼쪽 날개: `#2563EB`
- 오른쪽 날개: `#7C3AED`
- 몸통: `#172554`
- 얼굴: White / Navy

## 12.4 사용 위치
- 홈: “어디로 갈까요?”
- 경로 계산 중: 두 경로 비교
- 우회: 방향 전환 안내
- 미확인: `?` 표시
- 검수 완료: 체크 표시
- AR 화면: 작은 AI Co-pilot 형태

캐릭터가 AR의 주 시야를 가리지 않도록 작은 보조 요소로 사용한다.

# 14. 발표 스토리

NaVi는 처음부터 “AR 길찾기 앱”이라고 설명하는 것보다 다음 구조가 좋다.

```text
자동차에는 운전자의 판단을 돕는 ADAS와 AR Navigation이 있다.

하지만 이동약자의 보행 환경에서는
“이 길을 실제로 통과할 수 있는가?”를
판단해주는 시스템이 부족하다.

NaVi는 공공데이터와 AI로
보행 구간의 상태를 판단하고,

실제 통과 가능한 경로를 계산한 뒤,

AR을 통해 현장에서
사용자의 행동까지 안내한다.
```

핵심은 **자동차 기술을 그대로 복제했다**고 말하는 것이 아니라,

> **자동차에서 이미 익숙한 ‘인지 → 판단 → 경로 계획 → 안내’ 구조를 보행 접근성 문제에 적용했다**

고 설명하는 것이다.

# 15. 최종 포지셔닝

NaVi는 다음 중 하나로만 정의하지 않는다.

- 단순 길찾기 앱
- 단순 AR 앱
- 공공데이터 시각화
- 장애인 지도

정확한 포지셔닝은:

> **공공데이터 + AI Perception + Accessibility Path Planning + AR Guidance를 결합한 보행 의사결정 지원 시스템**

사용자에게는 더 쉽게:

> **접근성 경로 시스템 + AR 행동 인터페이스**

또는:

> **자동차의 ADAS 개념을 보행자의 이동에 적용한 AI·AR 접근성 내비게이션**

으로 설명할 수 있다.
